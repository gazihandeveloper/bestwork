# Responsive CSS research: container queries, viewport units, safe areas, 320px reflow

All claims below were fetched and read from the cited primary sources (MDN, web.dev, W3C/WAI, WebKit, Chrome for Developers, drafts.csswg.org). Nothing here is inferred from memory.

## 1. Container queries vs media queries

**Baseline status.** MDN's `container-type` page carries the Baseline badge **"Widely available — available across browsers since February 2023"**, with the caveat "* Some parts of this feature may have varying levels of support" ([MDN `container-type`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/container-type)). The same badge/date appears on [MDN `@container`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@container) and [MDN `container-name`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/container-name). web.dev's launch post states size container queries + container query units are "stable in all modern browsers" and lists Chrome 105, Edge 105, Firefox 110, Safari 16 ([web.dev, "Container queries land in stable browsers"](https://web.dev/blog/cq-stable?hl=en)).

**Syntax.** `container-type` accepts `normal | size | inline-size | scroll-state | anchored`; `inline-size` "establishes a query container for dimensional queries on the **inline axis**… Applies **style and inline-size containment**", and `size` "establishes a query container for container size queries in both the **inline and block** dimensions… Applies style and **size containment**" ([MDN `container-type`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/container-type)). The `@container` condition must specify a `container-name`, a `<container-query>`, or both; without a name, features are "evaluated against the nearest ancestor query container that has the matching `container-type`" ([MDN `@container`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@container)). Logical keywords `and` / `or` / `not` are supported, and queries "always measure the content box" ([same](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@container)).

```css
.sidebar { container-name: sidebar; container-type: inline-size; } /* or: container: sidebar / inline-size */
@container sidebar (width > 700px) { .card { font-size: 2em; } }
```

**Containment implications.** MDN's guide states these values "apply different types of size containment. `inline-size` containment on an element prevents its descendants from affecting its inline-size," and that because a `size` container is not sized by its children, "the container will collapse unless given an explicit size by setting its dimensions… or placing it into an explicitly sized layout" ([web.dev Learn CSS: Container queries](https://web.dev/learn/css/container-queries?hl=en)). MDN's containment guide adds that the `style` and `layout` values of `contain` "are automatically applied when using the `container-type` and `container-name` properties" ([MDN: Using CSS containment](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Containment/Using)). MDN also explains *why* containment is mandatory: "querying the size of every element in the DOM, all the time, would be bad for performance… Additionally, if a descendant style changed the size of the container element, an infinite loop could occur" ([MDN: Using container size and style queries](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Containment/Container_size_and_style_queries)). The CSS WG removed a `block-size` value from `container-type` outright: "Remove the `block-size` value from `container-type`, since single-axis block-size containment is not currently possible" ([CSS Containment Module Level 3, Changes](https://drafts.csswg.org/css-contain-3/)) — i.e. width-only (`inline-size`) or both-axes (`size`) are the only size-query containers.

**Panel whose width changes because a sidebar opens/closes.** MDN frames container queries as "an alternative to media queries, which apply styles to elements based on viewport size or other device characteristics" ([MDN: CSS container queries](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Containment/Container_queries)). web.dev is explicit about the use case: with media queries "you could query the size of the viewport, container queries enable components that can change based on where they are in the UI… enabling a card component that can lay out in one way when placed in a sidebar, and in a different configuration within a product grid" ([web.dev](https://web.dev/blog/cq-stable?hl=en)). The key numeric consequence is documented precisely: if `@media` breakpoints assume a 200px sidebar exists, "the size conditions for the `@container` rules should be around 200 pixels less—assuming that the 'container' element… won't include the sidebar" — i.e. a viewport media query cannot see the sidebar because a viewport-width change is not implied when the sidebar toggles ([web.dev, "How to use container queries now"](https://web.dev/blog/how-to-use-container-queries-now?hl=en)). Two further practical points from the same source: `:has()`-style detection is not required — the container is the DOM ancestor (`.content, .sidebar { container-type: inline-size }`); and a JS `ResizeObserver` + `CSS.supports('container-type: inline-size')` feature-detect fallback is offered for older browsers.

**When media queries are still required.** Verified as *scope*, not as an explicit "cannot" statement: web.dev says "With media queries you can adjust layouts based on the size of the viewport **or the type of device being used**" ([web.dev Learn CSS](https://web.dev/learn/css/container-queries?hl=en)), and MDN's `@container` reference defines container size descriptors as `width`, `height`, `inline-size`, `block-size`, `aspect-ratio`, `orientation` — page-level layout, `print`, and `prefers-*` features are not in that set. MDN's viewport meta documentation further confirms viewport-level concerns live outside container queries (`viewport-fit`, `interactive-widget` are meta-tag/UA concepts) ([MDN: viewport meta name](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/meta/name/viewport)). Treat "media queries are still required for page-level layout, `print`, and `prefers-*`" as **not directly quotable from the fetched sources** (see unverified section).

## 2. Viewport units for mobile browser chrome

**Definitions (MDN `<length>`, viewport-percentage lengths).** `vh` is "1% of the viewport height"; the small/large/dynamic counterparts are `svh`, `lvh`, `dvh`, and **`vh` is equivalent to `lvh`** ("Currently, all default viewport units (`vh`, `vw`, etc.) are equivalent to their large viewport counterparts"). Same for `vw`≡`lvw`, `vmin`≡`lvmin`, `vmax`≡`lvmax`, `vb`≡`lvb`, `vi`≡`lvi` ([MDN `<length>`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/length)).

- **Small viewport** (`sv*`): "the smallest possible viewport in response to browser interfaces expanding dynamically… the element will fill the screen perfectly without any of its content being obscured when all the dynamic browser interfaces are shown," possibly leaving empty space when they retract; sizes are **fixed and stable** unless the viewport itself is resized. Small units are described as "safer to use in general, but might not produce the most attractive layout after a user starts interacting with the page."
- **Large viewport** (`lv*`): "content might get hidden when browser interfaces expand"; also fixed and stable.
- **Dynamic viewport** (`dv*`): "sizes… are **not stable, even when the viewport itself is unchanged**," with an explicit warning: "can cause the content to resize while a user is scrolling a page. This can lead to degradation of the user interface and cause a performance hit."
- **Default viewport units**: "defined by the browser… could be equivalent to… small, large, an intermediate size between the two, or the dynamic viewport size." (All from [MDN `<length>`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/length).)

web.dev's article gives the mechanism: viewport size "is influenced by the presence or absence of dynamic toolbars" but "`vw` and `vh` sizes do not. As a result, elements sized to be `100vh` tall will bleed out of the viewport"; large = toolbars retracted, small = toolbars expanded; dynamic "is equal to the size of the small viewport" when toolbars are expanded and the large viewport when retracted, so `dv*` is "clamped between their `lv*` and `sv*` counterparts." Units shipped in Chrome 108; the article lists Chrome/Edge 108, Firefox 101, Safari 15.4 ([web.dev, "The large, small, and dynamic viewport units"](https://web.dev/blog/viewport-units?hl=en)).

**Caveats worth knowing.** From the same article: all viewport units "do not account for the size of scrollbars"; dynamic values do not update at 60fps and some browsers debounce by gesture; and the **on-screen keyboard is not part of the UA UI, so it does not affect viewport unit sizes in the default behaviour** — Chrome offers an opt-in to change that ([web.dev](https://web.dev/blog/viewport-units?hl=en)).

**Practical guidance for full-height app shells.** MDN's own trade-off summary is the strongest primary statement: `sv*` is safest against obscuring, `lv*` risks hidden content when chrome expands, `dv*` tracks chrome exactly but is unstable and costs performance. web.dev additionally notes that with `dvh` the unit recomputes as toolbars expand/retract. A concrete `100dvh` recommendation for an iOS/Android full-screen canvas was **not** found in these primary sources (see unverified section).

**`interactive-widget` / virtual keyboard.** Chrome on Android "will no longer resize the layout viewport, only the visual viewport" as of Chrome 108, aligning with Chrome on iOS and Safari on iOS; group-1 browsers (Safari iOS/iPadOS, Chrome/Edge iOS/iPadOS, ChromeOS) resize only the visual viewport so "computed values for viewport-relative units remain unchanged" and elements using `position: fixed` "remain in position and can be obscured by the OSK," whereas group-2 (Chrome/Firefox/Edge on Android, Firefox on iOS) shrink viewport-relative units. Via the meta tag: `resizes-visual` (default), `resizes-content`, `overlays-content`; e.g. `<meta name="viewport" content="width=device-width, initial-scale=1.0, interactive-widget=resizes-content">`. Caveats: only Chrome 108+ supports the extension at the time of writing, and it excludes Chrome on iOS/iPadOS (WebKit); Chromium WebView is unaffected ([Chrome for Developers, "Prepare for viewport resize behavior changes"](https://developer.chrome.com/blog/viewport-resize-behavior?hl=en)). MDN's viewport meta reference confirms the same three keywords and adds: "When the viewport gets resized, the initial containing block also gets resized, thereby affecting the computed size of viewport units" ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/meta/name/viewport)).

## 3. Safe area insets

`env()` accepts `safe-area-inset-top|right|bottom|left`: "the safe distance from the top, right, bottom, or left inset edge of the viewport, defining where it is safe to place content into without risking it being cut off by the shape of a non‑rectangular display… The values are `0` if the viewport is a rectangle and no features — such as toolbars or dynamic keyboards — are occupying viewport space; otherwise… a `px` value greater than `0`" ([MDN `env()`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/env)). MDN's guide adds the read-only, globally-scoped, case-sensitive nature, a `safe-area-max-inset-*` family ("static maximum value of their dynamic `safe-area-inset-*` variable counterparts"), and history: "Apple first introduced environment variables in the iOS Safari browser to enable developers to optimize layouts for irregular device displays" ([MDN: Using environment variables](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Environment_variables/Using)). `env()` is Baseline widely available since January 2020 ([MDN `env()`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/env)).

**viewport-fit requirement.** WebKit: `viewport-fit` "provides control over the insetting behavior… The default value of `viewport-fit` is `auto`, which results in the automatic insetting behavior… In order to disable that behavior and cause the page to lay out to the full size of the screen, you can set `viewport-fit` to `cover`" — using `<meta name='viewport' content='initial-scale=1, viewport-fit=cover'>`. After adopting `cover`, "it is immediately clear why it is important to respect the system's safe area insets: some of the page's content is obscured by the device's sensor housing, and the bottom navigation bar is very hard to use" ([WebKit, "Designing Websites for iPhone X"](https://webkit.org/blog/7929/designing-websites-for-iphone-x/)). MDN documents `auto | contain | cover` and states for `cover`: "It's highly recommended to use the safe area inset variables to ensure that important content doesn't end up outside the display" ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/meta/name/viewport)).

**Bottom sheet / fixed bottom toolbar.** WebKit's pattern, verbatim intent: apply padding only to elements containing important content, and **always keep a fallback declaration** — "For browsers that do not support `env()`, the style rule that includes it will be ignored; for this reason, it is important to continue to separately specify fallback rules for any declarations using `env()`" ([WebKit](https://webkit.org/blog/7929/designing-websites-for-iphone-x/)). The idiomatic form (WebKit's own example, using `@supports` to feature-detect `max()`):

```css
.toolbar {
  padding-bottom: 12px;                                   /* fallback */
  padding-bottom: env(safe-area-inset-bottom, 0px);
}
@supports (padding: max(0px)) {
  .toolbar { padding-bottom: max(12px, env(safe-area-inset-bottom)); }
}
```

WebKit notes insets "are not a replacement for margins" — in portrait `env(safe-area-inset-left)` resolves to `0px`, so use `max()` to keep a minimum margin ([WebKit](https://webkit.org/blog/7929/designing-websites-for-iphone-x/)). MDN documents the equivalent `env(name, fallback)` syntax and the fallback semantics: if the variable name is unrecognized "the fallback value is used. The fallback can be another environment variable, even with its own fallback. If no fallback was provided, the property or descriptor containing the `env()` function is invalid at computed-value time" ([MDN: Using environment variables](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Environment_variables/Using)).

## 4. Testing 320 CSS px reflow

**The criterion.** WCAG 2.2 SC 1.4.10 (Level AA) requires content be presentable "without loss of information or functionality, and without requiring scrolling in two dimensions for: Vertical scrolling content at a width equivalent to **320 CSS pixels**; Horizontal scrolling content at a height equivalent to **256 CSS pixels**." Note 1: "320 CSS pixels is equivalent to a starting viewport width of 1280 CSS pixels wide at **400% zoom**" (and 256px ↔ 1024px height at 400%). Note 2 lists two-dimensional exceptions: images required for understanding (maps, diagrams), video, games, presentations, data tables (not individual cells), "and interfaces where it is necessary to keep toolbars in view while manipulating content" ([W3C WAI, Understanding SC 1.4.10 Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)).

**Why 320/256.** "The value of 320 CSS pixels for vertically scrolling content was chosen as a reasonable minimum size that authors can achieve… generally corresponds to a desktop browser window set to a width of 1280px and the browser viewport then zoomed to 400%. It should be noted that **400% applies to the dimension, not the area**." The page also stresses that exact alignment is not required: at 300% on a 960px-wide window, or with a docked half-display, the equivalent viewport is what matters ([same](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)).

**Practical test method (C33's Procedure, verbatim steps).** (1) "Display the web page in a user agent capable of 400% zoom and set the viewport dimensions (in CSS pixels) to 1280 wide and 1024 high." (2) "Zoom in by 400%." (3) For content read horizontally, "check that all content and functionality is available without horizontal scrolling." (4) For content read vertically, check the same for vertical scrolling. Note: "If the browser is not capable of zooming to 400%, you can reduce the width of the browser proportionally. For example, at 300% zoom the viewport should be sized to 960px wide." Expected result: #3 and #4 are true ([W3C WAI Technique C33](https://www.w3.org/WAI/WCAG22/Techniques/css/C33)).

**Caveat on device emulation.** The Understanding page explicitly warns that fixed-dimension browsers "commonly [do] not adjust the fixed-dimension browser viewport to the 320 CSS pixel width," and that "if a web page can be viewed on a device where the sizing requirements of this criterion can be accurately tested, then it is on such devices where a web page's ability to meet Reflow is best to be determined" ([same](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)). It also notes browser-UI overhead in practice — at 400% zoom on a 1280×1024 laptop the measured viewport was 318px × 236px due to scrollbar/tab/address-bar chrome ([same](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)). Related sufficient techniques listed on that page: C32 (media queries + grid), C31 (flexbox), C33, C38 (width/max-width/flexbox for labels and inputs), SCR34, G206, G224, G225; advisory: C34 (un-fixing sticky headers/footers), C37 (`max-width` for images); failure F102 ([same](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)).

## 5. Avoiding horizontal scrolling; `overflow-wrap` / `word-break`

**C33 (fetched).** "Long sets of characters without a space, such as URLs shown as content, can break reflow when the page is zoomed. The objective of this technique is to present URLs without introducing a horizontal scroll bar at a width equivalent to 320 CSS pixels." By default browsers wrap long URLs at `&`, `/`, `-`, `?`, but "Sometimes these are not enough." Example 1's declarations: `overflow-wrap: break-word` ("Allows words to be broken and wrapped within words") and `word-wrap: break-word` ("the same non-standard alias"). It also notes: "Using a human readable text link, rather than a long URL, is better for usability and accessibility" ([W3C WAI C33](https://www.w3.org/WAI/WCAG22/Techniques/css/C33)).

**MDN property semantics.** `overflow-wrap` "applies to text, setting whether the browser should insert line breaks within an otherwise unbreakable string to prevent text from overflowing its line box"; `word-wrap` is its legacy alias. Values: `normal`; `anywhere` ("may be broken at any point if there are no otherwise-acceptable break points in the line. No hyphenation character is inserted… Soft wrap opportunities… **are considered when calculating min-content intrinsic sizes**"); `break-word` ("The same as the `anywhere` value… but soft wrap opportunities… are **NOT** considered when calculating min-content intrinsic sizes"). Crucially: "In contrast to `word-break`, `overflow-wrap` will only create a break if an entire word cannot be placed on its own line without overflowing" ([MDN `overflow-wrap`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/overflow-wrap)). `overflow-wrap` is Baseline widely available since October 2018 ([same](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/overflow-wrap)).

**Which to pick for account IDs / member codes.** MDN's Wrapping and breaking text guide: "In CSS, if you have an unbreakable string such as a very long word, by default it will overflow any container that is too small for it in the inline direction," and the default `overflow: visible` is deliberate ("doing something else could cause data loss… Messy overflow is at least noticeable"). If the box must be fixed-size, "the `overflow-wrap` property can help. This property will break a word once it is too long to fit on a line by itself." `word-break: break-all` "will break the word at the point it overflows… even if placing the word onto a new line would allow it to display without breaking" — useful "if you want to prevent a large gap from appearing… Or, where there is another element that you would not want the break to happen immediately after" (e.g. don't break immediately after a checkbox). `hyphens: manual` with `&shy;`/U+00AD gives controlled soft break points; `hyphens: auto` lets the browser hyphenate. Alternatives: `inline-size: min-content` to let a box grow to fit the longest word ([MDN: Wrapping and breaking text](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Text/Wrapping_breaking_text)). Practical reading: `overflow-wrap: break-word` is the minimal fix for IDs in narrow containers; `word-break: break-all` is the aggressive option that also breaks when a wrap would have sufficed, at the cost of ugly mid-token breaks; `overflow-wrap: anywhere` additionally affects min-content sizing (relevant inside grid/flex tracks, where `break-word` alone may not shrink the track).

Combined with the Reflow page's guidance that fixed/sticky sidebars and toolbars — "commonly toolbars, menubars, navigation and other 'sidebar' content may be presented with sticky or fixed positions at larger viewport sizes" — should become static or user-toggleable at small sizes, since otherwise they "obscure not only the focusable elements of the page… but significantly reduce the available space for reading" ([Understanding 1.4.10](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)).

## UNVERIFIED / COULD NOT CONFIRM

1. **"Media queries are still required for page-level layout, `print`, and `prefers-*`."** No fetched primary source states this as a rule. MDN/web.dev support it only indirectly (media queries target "the type of device being used"; container size descriptors are limited to `width`, `height`, `inline-size`, `block-size`, `aspect-ratio`, `orientation`). I did **not** fetch an MDN `@media` page containing an explicit statement that print/`prefers-*` cannot be container queries. Treat as supported-by-scope, not as a quote.
2. **A concrete `100dvh` recommendation for a full-height app shell / canvas on iOS Safari or Android Chrome.** Not found. [web.dev's viewport-units article](https://web.dev/blog/viewport-units) defines and compares the units but gives no `100dvh`-for-app-shell recommendation; [MDN `<length>`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/length) gives the trade-off (small = safest, dynamic = unstable/perf hit). The `100dvh` shell pattern itself is my synthesis of those two, not a cited recommendation.
3. **A web.dev article specifically on safe area insets.** `https://web.dev/articles/vh-dvh-safe-area-insets` returned **HTTP 404**. No web.dev safe-area page was located; safe-area claims here rest on [WebKit](https://webkit.org/blog/7929/designing-websites-for-iphone-x/) and [MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/env) only.

6. **Browser device-toolbar / responsive-mode specifics (preset widths, zoom steps in DevTools).** The task suggested "browser device toolbar, responsive mode, browser zoom steps."
